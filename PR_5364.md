## Description

Fix the recurring permissions warning for `storage/logs/teampass_background_tasks.lock` reported in #5364.

The file is created at runtime to prevent concurrent background handlers. With a common process umask of `0022`, PHP creates it as `0644`, while System Health expects runtime files to have no access for other users (`0640` or stricter). A manual `chmod` is not durable because the handler removes and recreates the lock.

This PR fixes the writers, without weakening the integrity or permission checks:

- Add shared, DB-free helpers that restrict each opened lock/signal to its existing permissions intersected with `0640`, before writing any content. Existing `0600` permissions remain unchanged, and the process-wide umask is never modified.
- Apply this policy to the background-task lock and trigger, and to the file-integrity scan and enqueue locks.
- Open locks without truncation. The background handler only replaces the PID after successfully acquiring its exclusive lock; a competing handler cannot erase the current owner's PID.
- Fail when a file cannot be secured. Reject symbolic-link and non-regular-file targets; keep Windows handling compatible with its ACL model.
- Make the scan-status probe open existing locks only, so polling cannot recreate a lock with default permissions.
- Add regression tests and document the runtime-file permission policy.

These files remain excluded from release checksum comparisons as runtime data, but stay in scope for the permissions audit. No exclusion rule or `app/files_reference.txt` change is included; manifest generation remains part of the release process.

Seven existing source-inspection assertions are sensitive to CRLF line endings (Health, LAPR wiring, security posture and user-field authorization); the password-strength sentinel compares slash-separated paths with Windows backslash paths; the LAPR catalog test expects a symbolic link, but `core.symlinks=false` checks it out as a text file containing its target path. These existing tests and the relevant source sections were not changed by this fix. The earlier LF archive run had only the path-comparison failure. The PHP 8.2 run also reported one symlink-privilege warning; PHP 8.3 reported that warning plus three temporary-directory cleanup warnings. The targeted runs above were warning-free. Linux CI remains required before merge.
- `php .github/scripts/check_table_prefix.php`: pass.
- Verified `app/files_reference.txt` is byte-for-byte unchanged and the committed Composer metadata remains production-only.

The new tests cover creation/recreation under umasks `0000`, `0002`, `0022`, `0027`, and `0077`; repair of existing permissive modes without replacing the inode or truncating contents; preservation of `0600`; signal writes; lock contention; invalid targets; and continued detection of unsafe runtime permissions. POSIX-mode and symlink checks are skipped where unsupported locally and must be confirmed by Linux CI before merge.

No live-instance UI, database, or user-role tests were run locally. Roles and personal-folder settings are not changed. Suggested lab check: as an administrator, enqueue an integrity scan and trigger background processing under the normal web/cron account; verify recreated locks/signals have `0640` (or the existing stricter mode), the permissions warning disappears in a fresh report, and concurrent handlers do not run together. Also confirm that an unrelated runtime file with unsafe permissions is still reported.
